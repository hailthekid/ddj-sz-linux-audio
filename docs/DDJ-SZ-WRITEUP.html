01

Why this is a “quirk,” not a driver

Linux already ships a generic USB Audio Class (UAC) driver, snd‑usb‑audio. Any device that implements the standard UAC 1.0/2.0 descriptors works with it automatically — the driver reads the device's own descriptors at enumeration and configures itself. That's why a generic USB headset just works with zero drivers to install.

The DDJ‑SZ doesn't implement UAC on its audio interface. It identifies as USB class 0xFF, “vendor‑specific” — meaning the OS can infer nothing from standard descriptors. Channel count, sample format, activation sequence: all of it is proprietary. Windows and macOS get a real Pioneer driver that hard‑codes this knowledge.

On Linux, snd‑usb‑audio has a quirks system (sound/usb/quirks.c + sound/usb/quirks‑table.h) built for exactly this: a table, keyed by USB vendor:product ID, that manually supplies what the driver would normally read from standard descriptors, plus — if needed — a small device‑specific activation callback. It is not a new driver; it's a data‑table entry inside a driver that already handles URB submission, PCM buffering, and ALSA registration for every other USB audio device on the system. The same mechanism already covers the Pioneer DJM‑750, DJM‑850, DJM‑900NXS2, DJM‑450, DJM‑V10, DDJ‑SX3, and DDJ‑RB.

What actually got added

One ~49‑line entry in quirks‑table.h describing the DDJ‑SZ's endpoints and format, and one new case in an existing switch statement in quirks.c, wiring its USB ID to an activation function. No new module, no new subsystem, no new files.

02

Capturing the protocol with Wireshark

With no public spec for a vendor‑specific interface, the only way to learn the protocol was to capture and decode what the official Windows driver actually sends the device — on the theory that whatever bytes make the real driver work will make any driver work.

USBPcap, a Windows kernel‑mode USB bus filter, captured raw USB traffic while the DDJ‑SZ was enumerated fresh, used for playback through Serato (so real music payload bytes would appear), and used for mic recording (so real capture‑direction payload bytes would appear too). The result — ddjdz.pcapng, ~91MB, ~118,000 USB frames — was analyzed on the Linux side with tshark:

Shell · locating the device in the capture
tshark -r ddjdz.pcapng -Y "usb.idVendor == 0x08e4" \
  -T fields -e frame.number -e usb.device_address \
  -e usb.idVendor -e usb.idProduct
# → device address 8, every later filter keys off usb.device_address == 8

USBPcap wraps every USB transaction in a 28‑byte pseudo‑header (IRP ID, status, URB function, bus/device/endpoint, transfer type, direction, data length) followed by the transferred bytes. Wireshark's dissector parses this automatically, exposing usb.setup.bRequest, usb.setup.wValue, usb.setup.wIndex, and — for completed transfers, in verbose (-V) output — a CONTROL response data field.

2a · Descriptor‑level facts

Filtering on GET_DESCRIPTOR responses (bRequest == 6) during enumeration confirmed USB ID 08e4:0191; interface 0 as class 0xFF with alt setting 0 idle (no endpoints) and alt setting 1 active (two isochronous endpoints); endpoint 0x01 OUT and endpoint 0x82 IN, both 1024‑byte max packet, interval 3.

2b · Confirming the format from real payload bytes

Max packet size alone was ambiguous: 1024 bytes/packet at a given rate is consistent with more than one channel‑count/bit‑depth combination — a competing 15‑channel, 16‑bit hypothesis was plausible on paper. This was resolved empirically, not by guessing: isochronous frames on endpoint 0x01 were de‑interleaved under both hypotheses and checked for internal coherence — does the result produce two channels whose waveforms correlate the way a real stereo mix should? The 10‑channel, S24_3LE (24‑bit packed, 3 bytes/sample) interpretation at fixed 44.1kHz produced coherent, correlated stereo on channels 0/1. The 15‑channel hypothesis didn't.

Channel mapping followed the same empirical method: channels 0/1 correlated with Master output content during playback → Master L/R. Channels 8/9 correlated with spoken audio during a mic test → Mic. Channels 2–7 were never isolated in the original capture and remain unmapped — a documented open item, not a blocker.

2c · Finding the activation sequence

Filtering control transfers in time order showed one immediately preceding the point where isochronous streaming actually starts:

Control transfer · sample‑rate SET_CUR
bmRequestType=0x22, bRequest=0x01 (SET_CUR), wValue=0x0100
wIndex=0x0082, wLength=3, data = 44 ac 00  // little-endian 44100

This request shape — SET_INTERFACE to alt‑setting 1, then this SET_CUR — is structurally identical to pioneer_djm_set_format_quirk(), a function that already exists in mainline Linux for the DJM‑750/850/900NXS2/450/V10. Those devices just call it with their own endpoint's wIndex. For the DDJ‑SZ that value is 0x0082 — not guessed, not copied from the DJM example, read directly off this device's own capture. This single finding is what made “no new driver” viable: the activation handshake reuses infrastructure that already exists.

03

Kernel build environment

Raspberry Pi OS “trixie” (Debian 13) ships kernel headers as Debian‑style packages pre‑matched to the running kernel, including a working Module.symvers and a /lib/modules/$(uname -r)/build symlink already in place — simpler than older Raspberry Pi OS releases assumed. Those packages only support building external modules, though; they don't ship in‑tree source like sound/usb/*.c. Full source, matched to the exact version, was still required.

  1. uname -r → 6.18.34+rpt‑rpi‑2712
  2. Matched the upstream branch on raspberrypi/linux via git ls-remote --heads — branch names follow rpi-<major>.<minor>.y, so rpi-6.18.y.
  3. git clone --depth=1 --branch rpi-6.18.y … — shallow, for speed.
  4. Installed missing build deps: bc bison flex libssl-dev libncurses-dev.
  5. Extracted the running config: sudo modprobe configs && zcat /proc/config.gz > .config (the configs module has to be loaded first — /proc/config.gz doesn't exist until then).
  6. make olddefconfig to reconcile against this tree's current Kconfig.
04

Applying and building the quirk

The new entry in quirks-table.h was inserted after the existing DJM‑750 entry (found via grep -n "0x08e4, 0x017f" as anchor), following the same QUIRK_DRIVER_INFO / QUIRK_DATA_COMPOSITE / QUIRK_DATA_AUDIOFORMAT structure every other entry uses — two audioformat blocks, one per endpoint direction, both declaring 10 channels, S24_3LE, interface 0, altsetting 1, fixed 44100.

sound/usb/quirks-table.h · new entry
{
	/* PIONEER DJ DDJ-SZ, 10ch in/out, S24_3LE @ 44.1 fixed */
	USB_DEVICE_VENDOR_SPEC(0x08e4, 0x0191),
	QUIRK_DRIVER_INFO {
		QUIRK_DATA_COMPOSITE {
			{ QUIRK_DATA_AUDIOFORMAT(0) {
				.formats = SNDRV_PCM_FMTBIT_S24_3LE,
				.channels = 10, .iface = 0, .altsetting = 1,
				.endpoint = 0x01, /* playback */
				.rates = SNDRV_PCM_RATE_44100, …
			} },
			{ QUIRK_DATA_AUDIOFORMAT(0) {
				.formats = SNDRV_PCM_FMTBIT_S24_3LE,
				.channels = 10, .iface = 0, .altsetting = 1,
				.endpoint = 0x82, .ep_idx = 1, /* capture */
				.rates = SNDRV_PCM_RATE_44100, …
			} },
			QUIRK_COMPOSITE_END
		}
	}
},

And a new case in the existing switch inside snd_usb_set_format_quirk():

sound/usb/quirks.c
case USB_ID(0x08e4, 0x0191): /* Pioneer DDJ-SZ */
	pioneer_djm_set_format_quirk(subs, 0x0082);
	break;

Built module‑only, not a full kernel rebuild:

Shell · module build
ARCH=arm64 LOCALVERSION= make -j$(nproc) modules_prepare
ARCH=arm64 LOCALVERSION= make -j$(nproc) M=sound/usb
# → sound/usb/snd-usb-audio.ko, modinfo confirms the new usb:v08E4p0191… alias
05

Debugging round 1: the module wouldn't have loaded

The first successful build carried a fatal, silent problem: modinfo reported vermagic: 6.18.45-v8-16k+ against a running kernel of 6.18.34+rpt-rpi-2712. Linux refuses to load a module whose vermagic doesn't exactly match uname -r. Two separate causes, diagnosed and fixed independently.

Wrong source commit

The shallow clone's branch tip had already moved on to 6.18.45 — newer than what's installed. Fixed by deepening the clone (git fetch --deepen=N, incrementally, until the range of SUBLEVEL values in Makefile across history spanned past 34), then scripting a search across every fetched commit for the most recent one where Makefile read VERSION = 6 / PATCHLEVEL = 18 / SUBLEVEL = 34. The working‑tree edits were stashed, the tree checked out to that exact commit, and the stash popped back on top — auto‑merged cleanly.

Missing local version suffix

Even at the right base version, the release string read 6.18.34-v8-16k+, not 6.18.34+rpt-rpi-2712. The -v8-16k piece came from CONFIG_LOCALVERSION baked into the pulled config — the raw upstream RPi default; the real packaging suffix is applied separately by Raspberry Pi's own build scripts, not stored in‑tree. Fixed by editing .config directly (CONFIG_LOCALVERSION="+rpt-rpi-2712"). That still left a trailing +, which the kernel's scripts/setlocalversion appends whenever the tree has uncommitted changes and LOCALVERSION isn't explicitly set on the command line — fixed by passing LOCALVERSION= (empty, but set) on every subsequent build.

Result

vermagic: 6.18.34+rpt-rpi-2712 SMP preempt mod_unload modversions aarch64 — exact match.

06

Installation

Before touching anything: confirmed snd_usb_audio wasn't currently loaded and no USB audio device was attached — so replacing the module carried no risk to an active session. The stock, xz‑compressed module was backed up to /root/ddj-sz-backup/, then replaced with the freshly built .ko, depmod -a refreshed the dependency database, and modprobe snd_usb_audio loaded it. dmesg showed only the expected “loading out‑of‑tree module taints kernel” notice — harmless, expected for any module built outside the distro's own pipeline — and no probe errors.

This install is persistent across reboots: the file was replaced in place under /lib/modules/ and will load automatically every boot. It only reverts if a future kernel package update reinstalls the stock module, at which point rebuilding from ~/projects/ddj-sz-kernel and reinstalling the same way restores it.

07

Testing round 1: playback confirmed, capture silently broken

With the DDJ‑SZ plugged in, lsusb showed clean enumeration and aplay -l / arecord -l both listed card 2: DDJSZ. /proc/asound/card2/stream0 matched the design exactly: 10 channels, S24_3LE, 44100Hz, correct endpoints both directions.

Playback — speaker-test -D hw:2,0 -c 10 -r 44100 -F S24_3LE -l 1 — opened cleanly and ran a full pink‑noise sweep with no xruns. (Its default -t wav mode is hardcoded to 48kHz/S16_LE regardless of -F/-r and fails hwparams against this fixed‑format device; dropping -t wav for the default sine/pink generator fixed it.) Independently confirmed audible — real sound out of Master.

Capture — arecord -D hw:2,0 -c 10 -f S24_3LE -r 44100 — ran without any ALSA/USB error and wrote a correctly‑sized WAV file. Per‑channel RMS/peak analysis (a small Python script over the raw 24‑bit packed samples) showed every sample on every one of the 10 channels was exactly zero — not quiet, a hard zero, for the entire recording. A true unbroken zero rarely happens from real analog noise floor; it's the signature of a data path that isn't delivering real samples at all.

The first run didn't rule out procedural error, so it was re‑run a second time with a live person talking continuously into the mic and the hardware gain confirmed up. Still a hard, uniform zero across all channels — a real capture‑path defect, not user error.

A red herring, ruled out

/proc/asound/card2/stream0 showed Implicit Feedback Mode: Yes on the playback stream, with endpoint 0x82 as sync source — even though the quirk table deliberately left USB_ENDPOINT_USAGE_IMPLICIT_FB unset (the SZ has genuinely separate IN/OUT endpoints and likely doesn't need it). ALSA auto‑detects this for an async OUT endpoint with no explicit sync endpoint. Not the cause here — capture was tested standalone, no playback stream open — but worth knowing if simultaneous playback+capture ever misbehaves later.

08

Root cause, found back in the pcap

The original handoff notes had already flagged, as a contingency, a block of vendor status‑query control transfers observed preceding the SET_CUR in the Windows capture — described only in paraphrase, with no exact wValue/wIndex. With capture broken and playback working, both driven by the same activation call, the working hypothesis was that this omitted block specifically arms the ADC/mic path. Re‑examining ddjdz.pcapng resolved it precisely:

Shell · isolating the vendor writes
tshark -r ddjdz.pcapng -Y "usb.device_address == 8 && usb.setup.bRequest == 3 && usb.bmRequestType == 0x40" \
  -T fields -e frame.number -e frame.time_relative -e usb.setup.wValue -e usb.setup.wIndex
# → exactly 6 matches, all clustered at t ≈ 3.65–3.69s, immediately after enumeration
# and never repeated anywhere else in the ~118,000-frame capture

That timing — once, at bring‑up, never again — is the signature of a one‑time arming sequence, not something that needs to run before every stream. Each response was pulled from the verbose (-V) CONTROL response data field, frame by frame:

Vendor arm sequence · six control transfers, once per device bring‑up
#write wValuewrite wIndexread lenresponse
10x01000x8002600 04 04 04 04 04
20x02000x8002600 04 04 04 04 04
30x03030x8002600 04 04 04 04 04
40x04030x8002600 04 04 04 04 04
50x050a0x8002600 04 04 04 04 04
60x00000x8003200 00

Every write shares bmRequestType=0x40, bRequest=3, wLength=0 — the payload lives entirely in wValue/wIndex, no data stage. Every read shares bmRequestType=0xc0, bRequest=0, wValue=0x0000, using the write's wIndex. Since the read response is identical regardless of what was written, the reads are almost certainly just status polling — but since it was genuinely unclear whether the read itself was needed to make the device process the write, the full write+read pattern was replicated exactly rather than guessing which half was load‑bearing.

09

The fix, and confirmation

sound/usb/quirks.c · ddj_sz_arm_quirk()
static void ddj_sz_arm_quirk(struct usb_device *dev)
{
	static const struct {
		u16 value; u16 index; u8 read_len;
	} cmds[] = {
		{ 0x0100, 0x8002, 6 }, { 0x0200, 0x8002, 6 },
		{ 0x0303, 0x8002, 6 }, { 0x0403, 0x8002, 6 },
		{ 0x050a, 0x8002, 6 }, { 0x0000, 0x8003, 2 },
	};
	u8 buf[6];
	unsigned int i;

	for (i = 0; i < ARRAY_SIZE(cmds); i++) {
		snd_usb_ctl_msg(dev, usb_sndctrlpipe(dev, 0),
			3, 0x40, cmds[i].value, cmds[i].index, NULL, 0);
		snd_usb_ctl_msg(dev, usb_rcvctrlpipe(dev, 0),
			0, 0xc0, 0x0000, cmds[i].index, buf, cmds[i].read_len);
	}
}

/* wired into the existing switch: */
case USB_ID(0x08e4, 0x0191): /* Pioneer DDJ-SZ */
	ddj_sz_arm_quirk(subs->dev);
	pioneer_djm_set_format_quirk(subs, 0x0082);
	break;

Unlike the Windows driver, which ran this once at enumeration, this runs on every snd_usb_set_format_quirk() call — potentially every stream open, not just once per plug‑in. A deliberate simplification: the six commands are cheap, synchronous, and idempotent (the response never depends on prior state), so re‑running them more often than strictly necessary is harmless and avoided building one‑time‑at‑probe hook infrastructure.

Module rebuilt, reinstalled, modprobe -r snd_usb_audio && modprobe snd_usb_audio. Card re‑enumerated identically as card 2: DDJSZ. Capture retested with the same procedure, this time with a live person talking continuously for the full window:

Capture retest · per‑channel signal, mic active
ChannelRMSPeakNote
0–3~46~220–250noise floor
4–7~185~800–880unmapped, elevated
81608.57543Mic — confirmed
91608.57543Mic — confirmed

Channels 8/9 show RMS roughly 8.7× higher and peak roughly 8.6–9.4× higher than the low‑numbered channels — exactly the signature of a live voice signal landing precisely where the original Windows capture said it should, appearing only after the arm sequence was added. Beforehand, an otherwise‑identical test produced a hard, uniform zero. dmesg showed no errors throughout.

Result

Both playback and capture confirmed working end‑to‑end with real signal, using ~125 total lines of quirk‑table data and activation code layered on the existing in‑tree driver.

10

Open items

  • Channels 2–7 remain unmapped to specific physical ins/outs (phono/line returns, USB monitor sends). Not required for basic Master + Mic use; would need a dedicated capture with a distinct known signal fed into each physical input, analyzed the same way channels 0/1 and 8/9 were.
  • Mixxx integration — package installed (2.5.0), but pointing its Sound Hardware preferences at the device and confirming the existing MIDI mapping still operates through Mixxx itself (versus raw ALSA, which is what's been tested) needs GUI interaction and physical hardware — left as a manual follow‑up.
  • Simultaneous playback+capture hasn't been tested. Given the implicit‑feedback auto‑detection noted in §7, this is the first thing to check if running both together produces drift, stutter, or xruns — the fix would be adding USB_ENDPOINT_USAGE_IMPLICIT_FB explicitly to the capture endpoint.
  • Upstreaming — close enough in pattern to the already‑merged DJM‑750/850/DDJ‑SX3 quirks to be a reasonable alsa-devel submission candidate. Not done as part of this pass.
